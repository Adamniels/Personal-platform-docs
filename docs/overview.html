Personal platform, design overview

A stable core, features built one at a time, and a shared brain that is the thing making it a platform rather than a pile of apps.

Status: exploratory, nothing built. Last updated 4 August 2026. Source of truth remains architecture-decisions.md and open-questions.md; this page is the synthesis.

The picture

Five regions. The numbered walkthrough below explains each one and why it is shaped that way.

Orange outline means evidence can never move it. Only Adam can.

Walking through it

1

Platform shape, why the brain sits in the middle

Each feature is fully isolated: its own frontend, its own backend, its own database. What they share is not code and not a database, it is a small set of contracts with the brain.

The rule doing the most work is that features never call each other. If the wiki wants something from learning, it asks the brain. Without that rule, eight features become dozens of point to point dependencies and the system stops being extensible. The brain also never reads a feature's database directly, because that would couple it to internal schemas that change. It calls a narrow read API the feature exposes.

The core is deliberately small and boring: authentication, routing, identity. It must never be down, so nothing interesting lives in it.

2

Evidence in, everything that ever happens lands in one table

Every observation from every feature goes into a single event table, forever, append only. One table rather than one per feature, because consolidation can then reason over events from features that did not exist when it was written. At single user volume the usual objections to this do not apply.

Two timestamps, not one. When it happened, and when it was recorded. This exists so that backfilling old knowledge works. Saying "I took that course three years ago" must not look like a fresh signal, and without both columns every recency calculation breaks the first time the feature is used.

Six kinds of event, distinguished by what can be learned from them rather than by who emitted them. Exposure means the system showed something. Engagement means what was done with it. Judgment means it was explicitly evaluated. Assertion means Adam stated something. Decision means a choice was made with reasoning. Activity means work happened, recorded deliberately uninterpreted so behavioural statistics are derivable years later.

Scope is topic and entity, never feature. Scope says what a claim is about, not where it fires. Allowing feature as a scope is how a system ends up concise in one place, verbose in another, for reasons nobody remembers two years later.

3

What is held, and the single rule that decides who wins

The stores are not an authority ladder. Which store a claim lives in tells you who is allowed to change it, and that replaces the old rule that explicit input always outranks inference.

Profile holds the things Adam is definitionally correct about: identity, goals, values, interests, working style. Evidence can never move these. At most it can raise a question.

Knowledge model holds what he knows and how well. He seeds it on day one, and evidence is allowed to correct it, because self assessed skill is one of the few things people are reliably miscalibrated about. This is not an exception to the rule, it is a different store with a different rule.

Reported history holds what he says happened. Nothing else in the system can confirm or contradict it, so it stands until he changes it.

Procedural rules are global, always, and only exist because he deliberately added one. Saying "be more concise" mid conversation applies to that conversation and nothing else. That single choice removed an entire category of complexity, because a rule born from one sentence is a generalisation from one data point, which the design refuses to do everywhere else.

4

Retrieval out, three things that were all being called decay

Confidence is how strongly the evidence supports a claim. It moves when evidence arrives and never with time. Currency is how likely the claim still describes now, derived from how long it has been since anything supported it. Status is simply active or inactive.

Neither number is stored. Both are computed from the evidence links at read time. A background job that walks the table lowering numbers is consolidation quietly rewriting memory, which is forbidden elsewhere in the design. Computing means the score can never drift from the evidence behind it, and "why do you believe this" is answered by the same structure that produced the score.

They combine per question, not in storage. Asking what Adam is into now wants currency to dominate. Asking what he has worked on over the years wants it ignored, since applying it there would hide the answer. One stored number cannot serve both.

Records have no currency at all. A record asserts nothing about the present, so the mechanic does not apply. That means "a decision made in 2026 must stay visible in 2030" is a consequence of what a record is, rather than a rule someone has to remember to enforce.

Conflicts get surfaced, not silently resolved. Scopes form a partial order, so there are three outcomes: a narrower scope wins regardless of age, an equal scope means recency wins, and two incomparable scopes cannot be ranked at all and must be handed back as a conflict. The obvious implementation picks a winner in all three cases, and would be silently wrong in the third.

5

Lifecycle, who is allowed to put something away

Consolidation proposes and never retires. It runs offline over the whole corpus, merges duplicates, links evidence to claims, and puts proposals in the review queue. It never silently rewrites and it never removes anything for being old or uncertain.

Only Adam retires. He can edit or retire anything in the brain, not only rules. Retired means it stops applying but stays visible in history and can come back. Nothing is ever destroyed.

Editing transfers provenance. Edit a claim the system derived and it becomes yours, which changes who is allowed to move it afterwards. Without this, a correction is treated as just another inference the system is free to revise.

Every edit or retirement records a judgment event. Otherwise the original evidence is still sitting there, consolidation runs, and proposes the same claim again. Retire, it returns, retire again. One event prevents the most irritating failure a memory system can have, and it lands the rejection in the evaluation set for free.

What we have

Twenty seven decisions, grouped by what they govern. Full reasoning lives in architecture-decisions.md.

Platform architecture

Isolation

  • The brain is its own service with its own database
  • Features own their data, the brain owns what it means about Adam
  • Features never call each other
  • The brain calls feature read APIs, never their databases
  • Not designing for standalone extraction, so no fallbacks or portability seams

Containment

  • Per feature code in the brain lives in one thin module each, written as needed
  • Unified interface facing out, separate modules facing in
  • The brain never decides a question belonging to a feature's domain
  • Each feature wraps brain access behind one internal port, for testability
  • Cross feature entity links live in the brain, stored generically

Shape and stack

  • Three feature tiers: federated, embedded, linked
  • Reminders are a delivery capability, not a feature
  • Python for anything AI shaped, C# for CRUD and infrastructure, TypeScript for frontends
  • Schema first contracts with generated clients, committed to from day one
  • Storage is Postgres plus pgvector, not markdown

Memory and events

What gets recorded

  • One event table for every feature, extensible by construction
  • Six event kinds, six categories of thing worth knowing
  • Two timestamps on everything, so backfill works
  • Payload version and idempotency key required from the start
  • Verbs are extensible but must declare evidence strength and polarity
  • Observation granularity is decided per feature, not globally

The filter

  • A fact belongs in the brain only if you can name the output that changes because of it
  • A feature promotes something only when it changes an output outside that feature
  • Interaction level tracking is ruled out globally
  • Behavioural inference deferred, but the recording that enables it is not

Structure

  • Four memory layers plus links, down from seven in v1
  • Claim versus record distinction lives in the schema
  • Topic vocabulary is canonical, provisional, or alias
  • Three relation kinds: topic to topic, entity to entity, memory to memory
  • Decisions are not structurally special and get no side table

The trust model

Authority

  • Authority follows the store, not the source
  • Profile and reported history move only by Adam's hand
  • The knowledge model is seeded then corrected by evidence
  • Rejection strength follows the same store rule, so no new rule is needed

Application

  • Records apply immediately, claims wait for consolidation
  • Standing rules are created deliberately, never inferred from one sentence
  • Conversation instructions are temporary but still recorded as evidence
  • Scope is topic and entity, never feature

Belief and correction

  • Confidence, currency and status are three separate things
  • Confidence and currency are computed at read, never stored
  • Nothing is deleted, and only Adam retires
  • Editing transfers provenance and records a judgment
  • Consolidation proposes, never silently rewrites

Process

How we know it is working

  • Retrieval evaluation exists from early on, run on every change
  • Every accept or reject in the review queue is a free labelled example, so rejections are kept
  • No weighted formula with invented constants; weights are earned through evaluation
  • Consolidation is idempotent and re runnable from the start
  • No LLM calls on the read path, so reads stay in the tens of milliseconds

What to build first

Profile, plus events, plus deliberately dumb retrieval, plus roughly ten evaluation cases. Nothing else. It is small, but from that point on every change is measurable, which is the whole point of sequencing it this way.

The order matters: there has to be a schema and a crude retrieval path before evaluation has anything to run against, so evaluation comes immediately after the simplest retrieval works rather than first.

One thing grew. Being able to edit and retire anything in the brain means the memory centre is a general item browser, not a profile page plus a rules list. That is not first milestone work, but it is where a meaningful share of the real build sits, so the milestone only stays honest if the browser is understood as coming later rather than being quietly implied by the word "profile".

Most of the highest value memory is manual anyway. Stable identity and working preferences are typed in. So the first useful version of the brain is a profile page and a retrieval call, and it already improves every feature that talks to it. Inference is what makes it compound, but it is not where the initial value comes from.

Costs accepted knowingly

Not problems to solve. Things chosen with the downside understood, recorded so nobody relitigates them later.

  • Going polyglot. Separate builds, separate tooling, no shared types, and contract drift caught at runtime instead of compile time. Mitigated by schema first contracts with generated clients on both sides.
  • The brain will not learn working style passively. Adam has to notice he is repeating himself and add a rule. The eventual fix is consolidation proposing rules from repeated occurrences, which is a much stronger basis than one sentence, so the capability is deferred rather than lost.
  • No cheap answer to "what do you believe right now". Everything is computed from evidence, so producing a full belief snapshot means running over the corpus. Materialising it is fine but it is a cache and needs invalidating on write, the same trap the profile snapshot already fell into once.
  • Belief has no natural cutoff. Since scores are a gradient, rendering a list of what the system believes needs a display threshold chosen somewhere.
  • Subjects can impersonate features. Nothing structurally prevents creating a subject that is a one to one proxy for a feature, which quietly recreates the feature scoping that was rejected. The guard is that it has to be stated as a subject and shows up in the rules list as one. Discipline, not mechanism.
  • JSON payloads mean no database level validation of feature specific fields, and the filter test has to be enforced by discipline rather than by friction. Accepted because the alternative is teaching the consolidator about every future feature.

Where the mess came from

Worth keeping, because it is the most useful lesson so far. Almost everything untangled on 4 August traced to a single root cause: one authority rule applied where it did not fit.

Saying "explicit user input outranks inference" sounds obviously right. It is right about preferences and wrong about self assessment, and reading it as one universal rule is what put skill levels into a store that could never correct them, and what let one sentence create a permanent global rule. Four apparently separate problems, one cause. Fixing the root closed an entire open question rather than answering it.

The general shape to watch for: a rule that is true in the case you first thought of, quietly applied to a case where the same words mean something different.
